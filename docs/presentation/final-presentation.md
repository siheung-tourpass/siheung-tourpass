# 최종 발표 준비 기준 — 시흥 투어패스

[문서 안내](../../README.md#관련-문서)

사용자가 제공한 최종 발표 안내에 따른 자료 구성·근거 준비·제출 점검을 담당한다. 지역 문제 가설과 검증 방법은 [지역 문제와 사용자 검증](project-validation.md)을 따른다.

## 발표·제출 조건

| 항목 | 기준 |
| --- | --- |
| 제출물 | 발표자료만 제출하며 별도 보고서는 첨부하지 않는다. 이 문서는 내부 준비용이다. |
| 발표 시간 | 최대 10분. 시연영상 재생시간은 제외한다. |
| 시연영상 | 핵심 문제 해결 흐름을 1~2분 내외로 권장한다. 음성 또는 자막을 넣고 유튜브 등에서 재생 가능하게 준비한다. |
| 영상 안내 | 목차에 전체 발표영상 링크·QR코드를 잘 보이게 배치하고 별도 서비스 시연영상과 구분한다. |
| 문의 | 최종 발표 관련 질의응답 게시판을 이용한다. |

## 발표의 핵심

발표자료만 읽어도 **시흥시의 문제 → 기존 서비스의 한계 → 해결 기능 → 구현·검증 결과 → 실제 활용 방안**을 이해할 수 있어야 한다.

| 심사기준 | 배점 | 자료가 답해야 할 질문 |
| --- | --- | --- |
| 지역연계성 | 20점 | 왜 시흥시에서, 누구에게 필요한가? |
| 문제해결성 | 20점 | 어떤 불편을 어떤 기능으로 해결했고, 효과를 어떻게 확인했는가? |
| 창의성 | 20점 | 기존 서비스보다 새롭거나 개선된 점, 보완·연결하는 지점은 무엇인가? |
| 완성도 | 20점 | 실제 구현 범위는 어디까지이며, 작동 여부를 어떻게 확인했는가? |
| 정책활용가능성 | 20점 | 시흥시의 어느 기관·서비스·업무에 어떻게 적용하고 운영할 수 있는가? |

기존 시흥시·공공기관 서비스의 개선·고도화·연계 방안을 구체적으로 제시한다. 신규 서비스도 기존 서비스나 지역기관 업무를 어떻게 보완하는지 설명한다.

## 발표자료 구성

아래 순서와 분량은 조정할 수 있다. 앞부분의 서비스 요약에 대상·문제·해결 방식·차별점을 집중한다.

| 순서 | 내용 | 필요한 근거·화면 |
| --- | --- | --- |
| 0 | 목차·영상 안내 | [발표·제출 조건](#발표제출-조건)에 따른 링크·QR코드 |
| 1 | 팀·서비스 요약 | 팀명·팀원·역할·서비스명, 누구의 어떤 문제를 해결하는지 한 문장으로 설명. 유사 주제 팀과의 차별점은 표지와 요약에 표시 |
| 2 | 시흥시에서의 필요성 | 구체적인 대상·상황·불편, 지역 통계·정책·뉴스의 출처와 기준일. 인터뷰·설문·현장 방문을 했다면 확인한 요구와 반영 내용 |
| 3 | 기존 서비스와 개선점 | 관련 공공·유사 서비스의 실제 화면과 이용 과정에 문제점 표시. 기존 기능과 개선·추가·연계 기능 비교표 |
| 4 | 해결 방식·핵심 기능 | 핵심 기능 2~3개와 대표 이용 흐름. `현재 문제 → 개선 방향 → 구현 방법` 연결표와 화면·일반인이 이해할 흐름도 |
| 5 | 구현 결과·개발 과정 | 제안 당시 기능을 완료·부분 구현·미구현으로 구분하고 시흥시 지원이 필요한 부분 표시. 실제 개발 화면, 핵심 구현 방식과 해결한 주요 문제, 데이터·API 연결 방식 |
| 6 | 서비스 시연 | 사용자가 핵심 기능으로 목적을 달성하는 영상. 로그인·메뉴 소개보다 문제 해결 흐름에 집중 |
| 7 | 검증·개선 결과 | [검증 기록 기준](project-validation.md#검증-기록)에 따른 실제 결과와 사용자 의견에 따른 수정 전후 |
| 8 | 시흥시 적용·운영 | 적용 기관·부서·서비스·업무, 도입 방식, 운영 담당·정보 갱신·비용·협조사항. 기관과 협의한 사실과 팀의 제안 구분 |
| 9 | 효과·한계·다음 단계 | 시민·지역기관·시흥시의 이점, 이번 학기에 확인한 효과와 향후 기대효과 구분. 남은 한계와 개선 방향 |

## 프로젝트 근거 연결

발표용으로 기능·정책 목록을 별도 관리하지 않고 아래 원본에서 근거를 가져온다. 요구사항에 적혀 있다는 이유만으로 구현 완료로 표시하지 않는다.

| 준비할 내용 | 확인할 원본·자료 |
| --- | --- |
| 지역 문제와 기능의 연결 | [지역 문제와 사용자 검증](project-validation.md#기획-근거). 문제 제안과 검증된 지역 현황을 구분하고 필요한 통계·공식 자료를 확보 |
| 제안 기능 대비 구현 범위 | 제안 당시 자료와 [공통·역할별 요구사항](../../spec.md), 실제 화면·코드를 대조. 구조·남은 작업은 [구현 계획](../../plan.md) 참고 |
| 데이터의 실제 사용 방식 | [데이터 수집 기준](../data-collection/common.md)과 [자료별 문서](../../README.md#데이터-수집검토). 실제 자료·공공데이터/API 연결·시연 데이터를 구분하고 실시간 연동 여부를 명시 |
| 작동 확인과 사용자 검증 | [테스트 안내](../../README.md#테스트)의 실행 결과와 [사용자 검증 절차](project-validation.md#검증-절차)의 실제 기록. 기능 시험과 사용자 검증을 구분 |
| 효과·활용 범위 | [효과 표현 기준](../../spec.md#범위)과 [검증 한계](project-validation.md#검증-한계). 도입·운영안은 현재 구현 범위 및 기관 협의 여부와 구분 |

기존 서비스에 기능이 없다는 주장은 실제 이용 과정·화면을 확인한 뒤 작성하고 확인일·범위를 남긴다. 미확보 수치·검증 결과·기관 협의 내용은 추정하지 않는다. 준비가 막힌 항목은 [구현 계획의 남은 작업](../../plan.md#남은-작업)에 대기 이유와 재개 조건만 기록한다.

## 작성·제출 점검

- 시흥시 심사위원이 영상·음성 없이도 이해하도록 그림·실제 화면과 짧은 개조식 설명을 함께 배치한다.
- 슬라이드 제목은 주장을 담은 문장으로 쓴다. 예: `핵심 기능` 대신 `관광지·행사·음식점을 한 여행에 담을 수 있다`. 수치가 들어간 주장은 확인한 결과만 사용한다.
- 기술 용어를 줄이고 시민의 이용 과정과 행정 업무의 변화를 중심으로 설명한다.
- 발표영상·음성에는 AI를 사용할 수 있다. 전체 발표영상·서비스 시연영상의 링크와 QR코드가 열리고 재생되는지 확인한다.
- PPT/PPTX 저장 시 글꼴을 포함하고, 변환한 PDF의 글자·이미지가 깨지지 않는지 확인한다.
- 제출 전 다섯 심사 질문의 답과 [발표·제출 조건](#발표제출-조건)을 모두 충족하는지 확인한다.
